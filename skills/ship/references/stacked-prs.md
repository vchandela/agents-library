# Stacked PRs

## Make it a native stack

- **Every stack of two or more PRs is a native GitHub stack before hand-off, by default.** On a native stack GitHub retargets the next PR to main and rebases it by itself after each merge, so the user merges bottom first with no wait. Plain chained branches do none of that: after a squash merge the next PR still points at the merged branch (the repo keeps it, `delete_branch_on_merge` is off), and each PR above then needs a replay and a fresh CI run. Example: artemis's eight-PR native stack merged in nine minutes on 2026-11-13; a seven-PR chained stack on 2026-11-16 would have needed six replays.
- **How:** with each PR's base set to the branch below it, check first that none is already in one (`gh api "repos/<o>/<r>/stacks?per_page=100"`, look for the PR numbers in an open stack), then `gh api -X POST repos/<o>/<r>/stacks -F "pull_requests[]=<bottom>" -F "pull_requests[]=<next>" ...`, bottom first. Name the stack URL (`https://github.com/<o>/<r>/stacks/<n>`) in the hand-off. If the call is refused, say so in the hand-off rather than handing over a chained stack silently.

## Pushing

- **Never a plain `--force`, and never amend or rewrite a pushed commit.** Fix with a new commit on the branch the fix belongs to.
- **The one allowed rewrite is a stack rebuilt onto a moved main.** Push each of your own branches with `git push --force-with-lease=<branch>:<sha you last checked> --force-if-includes`, so the push is refused if anyone else pushed since. Push only after every rebuilt commit adds and removes the same lines as the reviewed one.

## Keep every upper branch linear

- Each upper branch sits on the exact commits of the branch below, with no merge commits. When the lower branch gains commits, let the host move the stack (GitHub's stack rebase, or its retarget after the lower PR merges). Never merge the lower branch into the upper one by hand.
- **A merge commit carries nothing.** A fix or conflict resolution that exists only in a merge commit's tree is dropped when the host rebases the branch, and CI stays green because the lost lines usually have no test. Example: artemis outage-watch #1079 to #1093 went out as merge-commit tips, and every restack dropped fixes (6 files, then 3, then 2), each found only after the lower PR had merged.
- **A broken stack** (the host's rebase stopped on conflicts, or never ran): replay the upper PRs' commits onto main with `git cherry-pick`, resolving each conflict in the commit it belongs to, then push the same branches with the lease. The PRs keep their numbers and history. The reviewer reviews every conflict resolution before the merge. Example: artemis #1206 to #1215 were replayed onto main after #1222 conflicted with two of them.
- Give every review fix its own test where one can exist, so a lost line turns CI red.

## Merging

- **Before every merge, the first one included, run `references/stack-merge-check.sh <repo> <pr head> <approved previous head> <approved head>`.** It passes only when the head's tree equals the merge base with main plus the reviewed diff (applied with exact context), and no merge commit in range carries content (`git log --remerge-diff` shows no changed file). Any difference is a stop: restore the content in an ordinary commit, get the reviewer to approve it, then merge. Green CI does not show a lost line. Don't compare the new head with your own tree (it fails once main moves) or diff text (false alarms on `index` ids and `@@` numbers). Read the files it lists as changed by main too, because `git apply` places a hunk by its context.
- Before the first merge of a stack, `git rev-list --merges origin/main..<top>` must be empty or content-free; if not, rebuild with the replay remedy above before any merge.
- On GitHub, a PR inside a stack refuses `gh pr merge` and the plain merge API. Where the repo has a `scripts/land`, land bottom first through it; it runs, per PR, `gh api -X PUT repos/<owner>/<repo>/pulls/<n>/merge-async -f merge_method=squash -f sha=<full head sha> -f commit_title="<PR title> (#<n>)"`. A repo without one runs that command directly. Without `commit_title`, a one-commit PR takes the commit subject, not the PR title. GitHub is meant to retarget the next PR and rebase the branches above.
- **A stack merges one PR at a time, never in one click.** On artemis on 2026-11-12, #1846 merged at 15:03:52Z, GitHub rebased #1847 onto main by itself at 15:03:57Z, and #1847 merged at 15:04:13Z, so it took two merges. #1860 then #1861, and #1835 then #1841, went the same way. A bypass merge of the top PR is refused too: on 2026-11-13, `merge-async` with `bypass_rules=true` on #1898, the top of stack #1899, returned HTTP 400 "Rules can only be bypassed when merging the bottom-most unmerged pull request in the stack" and merged nothing. Plan one merge per PR, bottom first, with the check before each. With bypass this is fast: the same eight PRs (#1885 to #1891, #1898) merged bottom first between 14:51 and 15:00 that day with no CI wait between them, because each head's tree equalled a tree CI had already passed, and main's tree equalled the merged head's tree after every merge.
- **Don't count on GitHub's restack.** It ran by itself on every artemis stack merged on 2026-11-12 and 13 (above), but on artemis on 2026-10-10 it never ran after a squash merge, from the PR page or `merge-async`: the PR above kept its old base and the stack still counted the merged PR. The admin override (`-F bypass_rules=true`) works only on the bottom-most unmerged PR. What worked: dissolve the stack (`POST repos/<o>/<r>/stacks/<n>/unstack`), then for each PR, bottom first, replay the remaining commits onto main, check their lines, push with the lease, point the PR at main (`gh pr edit <n> --base main`), wait for green CI, run the check, and merge with `merge-async`.
- After each merge, diff every rewritten branch against its reviewed tree (it should be empty). Green CI carries over when the new head's tree equals a tree that already passed CI (`git rev-parse <new>^{tree}` against the tested head's tree), because CI's result depends only on the files. Compare against the tree CI actually tested: a pull_request run tests GitHub's merge of the head into its base, so it counts only when the head already contained its base, and a push run tests the commit itself. Name the run id and the tested commit in the hand-off. Wait for a fresh run only when the trees differ, for example because something else landed on main in between. Example: artemis #1494 to #1497 on 2026-10-28, where each run takes 12 to 15 minutes plus queue time.
- Merge order follows only real edges. Name what each "after" protects. Example: on the same stack only "runbooks #112 after #1495 deploys" was real, and the switched-off poller and the read-only UI could merge right behind #1495.
