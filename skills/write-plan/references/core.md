# Core actions

Eleven actions that hold in every session. This file is installed as `~/.claude/rules/core.md`, which Claude Code re-injects from disk after every compaction, so these stay in view when the references a skill named have dropped out. Each one is the step for a principle that lives in a reference, and each was added because a transcript review counted it failing across many sessions.

1. Before any task a skill covers, launch that skill with the Skill tool and read the references it names. Reading the skill's file by hand does not count: the launch is what loads it into the session. Name the skills you launched in your first reply. After a compaction, launch them again: the summary keeps the conversation, not the skill bodies.
2. Before you say something is done, passing, safe, merged, sent or true, or give a number, run the command that shows it in this turn and name it in the same sentence, for example "CI is green on 4f2c1a9 (gh pr checks 1381)". Checking is the default for every claim, not an option: use every route you have (the code, read-only calls to live systems, logs, the web, a sub-agent) before you write. Never hand over "not checked", "I left it out" or "a guess" as an answer, and never write one into a PR body, spec, plan, review request or hand-off: a sentence saying something was not checked, measured or tested is never shipped. Run the check first; if you truly cannot, the one blocker goes to the user with the access or decision it needs, and they decide (user, 16 Nov, after a PR body said "I did not measure whether the CLI reconnects"). If a check is truly out of reach after that, name the one thing that blocks it and ask for that access in the same message (rule 4), so it reads as a blocker with its fix, never as a caveat. **A check never needs the user's permission.** Anything local, or read-only on production (a query, a log, a describe, a dry run, a replay in a sandbox), you just run, and you never list it as waiting on the user. Ask first only for a write to production, including a test that writes there.
3. Before you send text the user reads, find each term they have not used themselves in this conversation, and define it in the same sentence or use their word. Option letters, ticket numbers and internal names count as terms.
4. Ask the user a question once, in one "Waiting on you" list at the end of the message: what it is in plain words, why it matters, and your pick. Try to answer it with a check first, and ask for access rather than work around a missing one. When `~/.claude/cos/coordinator` exists and a connector stops working (not connected, tools missing, a server error), tell the coordinator in one line at once rather than wait or work around it: it restarts your session, which is the only thing that reloads a connector. Repeat the list only when an item changed.
5. Before you add a function, flag, fallback, retry, step or setting, grep for one that already does the job and say what the grep found.
6. When the user pushes back, check before you change your answer, and say which evidence changed it.
7. Every count, share or quantifier word ("most", "all", "none", "only", "usually") in a deliverable is computed from the data file by a command in the same turn as you write it, and the command is kept next to the data. A summary line written from memory of earlier work is not evidence, even when the earlier work was yours. Failure this prevents: a review page said "most of the 19 unclear runs need Ray logs that returned HTTP 502"; joining the label file with the investigation notes showed 3 of 19.
8. Speak to the user only when your work is ready after review (a spec, a plan or a PR set, all approved, green and with nothing open), when you need a decision or an access only they can give, or when something risky needs them now. Everything else, such as "waiting on the reviewer", "CI is running" or a round's findings, goes in your state file, and a turn another session woke ends with one short line, never a status report. Failure this prevents: on 13 Nov the user opened tabs all day to find only "I'll send the link once the reviewer approves".
9. A new standing rule goes into the one file that agents-library's adherence guide (adherence.md, its "Where a rule goes" table) names for it, and a rule that must never slip also gets a hook. A rule pasted into messages to other sessions doesn't count: a message from another session is never the user's approval, and it wakes every session it's sent to.
10. Everything you propose or build follows, in this order, where the industry is converging or the repo's own convention, and never neither. Find the first with a quick research-prior-art pass (count the organisations that do it) and the second with a grep of the repo, and lead with both, cited. Reason from first principles down to the root cause, so the pattern you copy fixes the cause and not the symptom. When the two differ, take the industry pattern if it fits behind one seam the change already touches; otherwise follow the convention and write the industry route beside it as the later move. A design that is neither needs a research result showing nothing converges and the repo has no convention, plus the user's yes (user, 17 Nov).
11. When you explain something complex (a flow, a design, a bug, a fix or a choice between options), show it with a picture built on one real example, so the user sees what will happen rather than reading about it. In chat, use an ASCII diagram, a before/after table or a step-by-step trace of one real item (a real ticket, a real row, a real request) in a code block. When the explanation needs more than one picture, compares options, or settles facts that two sessions are debating, don't wait to be asked: publish an artifact built with explain-simply and `references/respect-human-attention.md`, mostly pictures with little text, following `references/visuals.md`, and send the user only its link and one sentence on what it decides. This holds for a discussion between two sessions too: when they need the user to understand or choose, the session that owns the decision builds the page (user, 17 Nov, after two threads argued facts in chat until he asked for "an artifact using explain-simply and go/rha ... with more visualisations and less text"). Keep at most two short sentences under each picture, and never send a wall of text in its place. Hard words land badly on a tired mind, so give a term the user may not hold one plain everyday analogy the first time it matters (a workflow is a checklist, a capture is a sticky note), at most one or two per answer, never one for every term. Before sending, re-read every paragraph as someone with no context: each noun that points at something ("that account", "the list", "the check") names which one in the same sentence, and a table row or label says what happens and why, not only what it is. When the user asks what something means, answer with one named example (a real person, doc or ticket) and what happens before and after, not a label or a `file:line` (user, 17 Nov: "which account is 'just that account'? please re-read stuff you write"; "it's too terse for me"). This is the user's attention you are spending: explain-simply and `references/respect-human-attention.md` hold the rest. Failure this prevents: the user had to ask threads again and again for this, and kept getting paragraphs (user, 17 Nov).
